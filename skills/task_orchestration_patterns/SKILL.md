# タスク実行パターン（監査・盲検再現・合議・並列）

## 発動とパターンの選択

- ユーザーがパターンID、パターン名、または合言葉で指定したら、このスキルを使う。Aは「パターンA」「監査付きで」、Bは「パターンB」「盲検再現で」「再現テストで」、Cは「パターンC」「合議して」「マギで決めて」、Dは「パターンD」「並列で調べて」が目印である。

- パターンが指定されていない場合、タスクの性質から合うパターンを1つ選び、着手前にどのパターンで進めるかをユーザーに宣言する。

- パターンを選んだら、実行前にそのパターンの詳細ファイルを読み、共通手順はこのファイル、パターン固有の手順とパラメータは詳細ファイルに従う。

  - A 監査付きは `references/pattern-a-audit.md` を読む。
  - B 盲検再現は `references/pattern-b-blind-reproduction.md` を読む。
  - C 合議は `references/pattern-c-council.md` を読む。
  - D 並列は `references/pattern-d-parallel.md` を読む。

## パターンの概要

- A 監査付きは、作り手と独立した監査役を分ける型である。成果物の出来が物差しと比べられる場合に使う。

- B 盲検再現は、文脈を持たない再現役が再現パッケージだけから成果物を再現し、文脈を持つ検証役が照合する型である。テスト対象は再現物ではなく再現パッケージそのもので、プロンプトや仕様書の再現可能性を検証する場合に使う。

- C 合議は、判断基準の違う複数のメンバーが独立に判断し、決め方に従って集約する型である。トレードオフのある意思決定に使う。

- D 並列は、重視する観点の違う複数の調査役が独立に調べ、統合役がまとめる型である。範囲の広い調査に使う。

## 受付とパラメータ検証

- ユーザーの依頼と、メモリや案件ファイルから分かる既知の情報を組み合わせて、そのパターンの発注票を作る。すでに分かっていることを聞き返さない。

- 詳細ファイルで必須とされたパラメータが1つでも欠けていたり曖昧だったりしたら、実行を保留する。サブエージェントの起動も成果物の作成も始めない。

- 保留したら、欠けている必須パラメータをまとめて一度に質問する。選択式にできる項目は選択肢で示し、ユーザーが一度の返信で全部に答えられる形にする。

- 任意パラメータが欠けている場合は、詳細ファイルの既定値を使う。使った既定値は、着手時の報告でユーザーに明示する。

- パラメータが揃ったら、パターン名と確定したパラメータの要約をユーザーに示してから実行に入る。ユーザーが事前確認を求めた場合は、要約の提示で止まる。

- 実行の途中で必須パラメータの不足や矛盾に気づいたら、その時点で止めてユーザーに確認する。不足を推測で埋めて続行しない。

## 共通の実行作法

- 主担当の Muse がディレクターを務める。タスクを分解し、各サブエージェントへ自己完結した指示を渡し、結果を統合してユーザーに報告する。

- サブエージェントへの指示には、役割、確定したパラメータ、入力、求める出力の形、止まる条件を含める。サブエージェントはこの会話の文脈を見られない前提で書く。

- 判定や判断を担うサブエージェントの独立性を守る。監査役、合議のメンバー、並列の調査役は、他の担当の結論を見る前に自分の見解を作る。

- サブエージェントからの報告は、結果、根拠や出典、不確実な点、未実施の項目を含む形で受け取る。作り手の自己申告だけを品質の証拠にしない。

- パラメータで決めた人数やループ上限を超えて続行しない。上限に達しても収束しない場合は、条件を勝手に緩めず、状況と選択肢をユーザーに上げて判断を仰ぐ。

## ユーザーへの報告

- 報告では、使ったパターンとパラメータ、各担当の寄与、最終結果を分けて示す。

- 合議の少数意見や並列調査の矛盾点は、統合の際に消さず、反対意見として残して示す。

- 不合格のまま終わった監査や決着しなかった合議は、成功したように見せず、その状態のまま報告する。
