# パターンA 監査付き

作り手が成果物を作り、独立した監査役が物差しと照らして合否を判定する型。通過しない場合は理由つきでリテイクし、上限回数までループする。

## 必須パラメータ

- 成果物は、作るものを具体的に指す。対象が特定できなければ必須パラメータ不足として質問する。

- チェック内容は、監査役が判定する項目の一覧である。各項目には、判定の物差しとなる参照先や基準を含める。項目が言葉だけの感想で終わり、比べる相手が示されていない場合は不足として質問する。

- ループ上限は、リテイクの最大回数を数で示す。初回納品はループに数えない。

## 任意パラメータ

- 作り手への制約は、使う道具、形式、守るべき条件である。指定がなければ案件の既存ルールに従い、その旨を着手時に明示する。

- 監査役の人数は既定で1人である。チェック内容が性質の違う群に分かれる場合は、群ごとの監査役を提案してよいが、人数を増やす前にユーザーに確認する。

- 合格の扱いは既定で全項目通過である。一部の項目を努力目標として外す場合は、ユーザーの指定があったときに限る。

## 質問のしかた

- チェック内容が曖昧な場合は、候補となる項目を具体的に挙げて、どれを物差しにするかを確認する。抽象的な問いだけで済ませない。

- ループ上限が未指定の場合は、回数の候補を示して選んでもらう。回数はコストと時間に直結するため、既定値で勝手に決めない。

## 実行手順

- ディレクターは作り手へ、成果物と制約を渡して発注する。監査役の詳細な採点観点は作り手へ渡さない。

- 作り手は成果物と自己申告を納品する。自己申告は動作確認や手順の適合の報告にとどめ、品質の保証として扱わない。

- 監査役は、成果物を見る前にチェック内容と物差しを読み、判定の観点を固める。その後に成果物そのものを開いて見て、項目ごとに通過か不合格かを理由つきで判定する。

- 不合格の項目がある場合、ディレクターは判定理由をリテイク指示に翻訳して作り手へ戻す。監査役の文章をそのまま転送しない。

- リテイクと再監査をループ上限まで繰り返す。上限に達しても通過しない場合は、残った不合格項目と理由をユーザーに報告し、続行するか条件を変えるかの判断を仰ぐ。通過していない成果物を納品扱いにしない。

## 報告の形

- チェック項目ごとの最終判定と理由、使ったループ回数、ラウンドごとの主な変更点を示す。

- 上限で止まった場合は、その状態を最初に明示する。
